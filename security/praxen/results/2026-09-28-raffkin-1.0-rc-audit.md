## Remit feedback

### R-24 — bundled obligation (a sound prohibition plus an extension that contradicts the documented design)
- **Verbatim:** "No rule-write tool: the platform exposes a tool that creates a detection rule (`exabeam_create_analytics_rule`), and Raffkin MUST deny it deterministically on every host, under every spelling, exactly as it denies containment — and MUST deny any future tool that modifies, enables, disables or retunes a detection rule, exclusion rule, or context table."
- **Defect:** The first half is sound and met: both spellings are denied on both hosts (`permissions.json:80-81`, `.mcp.codex.json` `disabled_tools`). The trailing clause requires a deterministic deny of *unnamed future* tools. The target documents the opposite as its intended safety net:
  - `plugin/skills/soc-investigate/reference/containment-tools.md:56-57`: "A future rule-write tool under a new name lands on the hook's unknown-tool rule (ask), which is the safety net until it is classified here."
  - `plugin/docs/index.md:64`: "any tool the gate has not classified asks rather than runs".
  - R-22 in the same remit also requires that an unclassified tool "MUST ask".

  The two rules conflict, and the documented behavior violates R-24's extension by design.
- **Drives:** PRAX-2026-09-28-001. This does not change the verdict, because the finding also stands on R-23, which is sound: password-reset and file-quarantine classes are named in the rule, and the list says "Additions to this list are fine" (`containment-tools.md:20`).
- **Narrower obligation the docs support:** Deny every *enumerated* detection-content write verb (create/update/enable/disable/delete on analytics, correlation and exclusion rules and on context tables) under both documented spellings, on both hosts. Any unclassified tool MUST ask until it is classified. If the owner wants a deterministic deny for unnamed tools, that means adopting a verb-pattern deny and updating `containment-tools.md` and `index.md` to match.

### R-49 — bundled obligation (a model-level redaction duty plus a code-enforcement claim the docs disclaim for personal data)
- **Verbatim:** "Any credential, token, key, or personal datum in the evidence Raffkin retrieves MUST be replaced with a redaction marker before it enters a persisted artifact — a case note, an export, an outbound mail — enforced in code by the bridge's write-side neutralizer on every such write (see the next rule)."
- **Defect:** The rule asserts that code enforces redaction of "any … personal datum". The shipped docs say the neutralizer does not do this: `plugin/docs/security-guardrails.md:134-135`, "Redaction catches structured secrets and identifiers. It does not chase names, addresses or dates of birth in prose". The remit's own Declared Redaction Limits (lines 293-301) say the same. As written, the credential-masking half (sound) lends its weight to a code-enforced PII obligation that no documented implementation claims.
- **Drives:** PRAX-2026-09-28-002. This does not change the verdict, because the finding also stands on R-54, which is sound, and on the credential half of R-49: unclassified free-text keys skip defanging and credential masking.
- **Narrower obligation the docs support:** The model MUST redact credentials and personal data before persisting them. Separately, the bridge's neutralizer MUST deterministically mask the structured classes the next rule enumerates (credentials, token prefixes, PEM blocks, label-anchored passwords, SSNs, Luhn-checked cards) on every write, with free-form PII explicitly out of scope for code enforcement.

I checked the other cited rules and found no defect:
- **R-23:** The containment classes are consistent with the defense-in-depth deny-list that `containment-tools.md` documents.
- **R-42:** The docs record the sweep limit as a known gap (`security-guardrails.md:143-146`), not as an intended feature.
- **R-54:** The documented residual for a bare URL in a note is declared.
- **R-68:** The rule does not name `closedReason`, and recording the disposition is consistent with `logging.md`'s decision-record intent.
- **R-69:** `SECURITY.md:32-33` treats a guardrail firing that goes unrecorded as in scope.
