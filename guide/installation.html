Installation & setup

Raffkin is a plugin for Claude Code, OpenAI Codex and Google Antigravity that works your Exabeam New-Scale tenant through the Exabeam MCP, Exabeam's tool interface for AI agents. Setup is the same shape on all three hosts: install the plugin, add one credentials file, check, and run your first investigation. Five minutes.

On all three hosts the safety gate is on from the moment the plugin is installed: containment is never executed, and in an attended session dismissing an alert or closing a case always asks you first. Nothing to configure for that. On Claude Code and Antigravity the gate is a hook inside the plugin; on Codex it comes from the approval policy the package sets.

Start a session with permission prompts turned off and the two halves part company. Containment stays refused on every host — on Antigravity that is measured, not assumed. The ask does not hold everywhere: on Claude Code a dismiss or close still needs a yes, and if nobody is there to give one the call is refused; on Antigravity the host overrides the gate's ask and the call runs unasked, so read "always asks you first" on that host as attended sessions only. See What is different on this host.

Antigravity differs in what has been tested, not in what is enforced — no release has been red-teamed on a Gemini model. Read What is different on this host before you install there.

Before you start

  • A host agent: the claude CLI (Claude Code), the codex CLI (Codex) or the agy CLI (Google Antigravity), signed in.
  • On Antigravity, two things that have nothing to do with this plugin — check both first. The plugin, the gate and preflight.sh all install and report healthy without a session ever being opened, so nothing else in this guide will warn you about either. agy -p "hi" answering is the one test that covers both.
    • A Google account Antigravity accepts. Signing in and being let in are separate gates: agy completes the OAuth flow and then refuses the session with "Eligibility check failed: Your current account is not eligible for Antigravity. Try signing in with another personal Google account." We hit this on a managed Google Workspace domain — which is what an analyst at a company has. Ask whoever administers your Google tenant whether Antigravity is enabled for it.
    • antigravity.google reachable from your network. A corporate secure web gateway may reset it while every other Google domain passes. On Zscaler we measured exactly that: accounts.google.com 302, google.com 200, gemini.google.com 200, cloudcode-pa.googleapis.com 404 — and antigravity.google failing the TLS handshake outright (curl: (35) Recv failure: Connection reset by peer), which in a browser shows up as ERR_CONNECTION_RESET on the consent page. That domain is the OAuth callback, so sign-in cannot complete until it is allowlisted. Check it with curl -o /dev/null -w '%{http_code}\n' https://antigravity.google/ — anything other than 200 means the login will fail no matter how many times you retry it.
  • A supported model. On Claude Code, Sonnet 4.6 or newer, or Opus; on Codex, GPT-5.6 Terra or Sol. Smaller models (Haiku, Luna) are not supported. See Security for how the supported models are validated. The Gemini models Antigravity runs are not in that validation set — no release has been red-teamed on one, so treat Antigravity as unvalidated on the model axis. The gate itself runs there; it is the model behind it that is untested.
  • uv 0.5.23 or newer on your PATH. It runs the bundled Exabeam connector and installs the connector's own Python dependencies; there is nothing to pip install. Those dependencies are pinned by hash, and uv refuses to start the connector if the pin cannot be honored, which is why the version matters (uv self update brings an older uv current).
  • python3 (3.7 or newer) on your PATH — Claude Code and Antigravity. The safety gate is a small Python script the host runs before each Exabeam call. On Claude Code, without python3 every gated call is refused. On Antigravity the hook falls back to uv, which you need anyway, so the gate still runs — and if neither is present, every Exabeam call is refused there too, with a message naming what is missing. Either way you lose the plugin, not the control. macOS and most Linux distributions already have python3 (python3 --version). Codex does not need it.
  • An Exabeam New-Scale API key and secret, created under Settings → API Keys in your New-Scale console. Keys don't carry a role — you grant them access entitlements, and Raffkin gets exactly what the key was issued with. Entitle the key to read alerts, cases, events, threat summaries, MITRE coverage and detection content (rules, parsers, context tables), and to create cases and write case notes; a read-only key investigates fine but cannot record an outcome. The exact list is under Key entitlements below.
  • Your New-Scale region. It is the <region> part of https://api.<region>.exabeam.cloud/mcp, for example us-west. Most tenant console URLs contain it — read it from the address bar. Some named environments (for example a demo or a dedicated tenant) have no region in the URL; ask your Exabeam administrator which region hosts them. The Region Deployed field under Service Health and Consumption → License View is not reliable for this — it may show a country rather than the hosting region.
  • Windows: Raffkin is not supported natively on Windows; use WSL. The diagnostics and the safety gate are shell scripts and Python, and the credentials file below is protected by Unix file permissions, which Git Bash on NTFS does not enforce — so Git Bash can run the scripts but leaves your key and secret unprotected. There is no PowerShell path.
  • Exabeam customers: the supported build is delivered through the Exabeam Plug-in Catalog, with its own install command. These instructions cover the community release; see Support.
  • Your own subscription. Raffkin runs inside your Claude Code or Codex plan. An investigation is a long agent session and is billed by your provider like any other.

Quick start — Claude Code

1. Install the plugin.

claude plugin marketplace add open-agent-ai-security/plugins
claude plugin install raffkin@open-agent-ai-security
claude plugin list      # expect a block for raffkin@open-agent-ai-security ending in: Status: ✔ enabled

If the block shows an error line under it, the plugin installed but did not load — see Troubleshooting.

2. Add your credentials. One file, in your home directory:

cat > ~/.exabeam-mcp.env <<'ENV'
EXABEAM_MCP_URL=https://api.<region>.exabeam.cloud/mcp
EXABEAM_API_KEY=your-key
EXABEAM_API_SECRET=your-secret
ENV
chmod 600 ~/.exabeam-mcp.env

Replace <region> with your region. The URL must be https://. Then restart Claude Code, or run /reload-plugins inside it — the connector reads this file when it starts.

Using a secrets manager instead. The connector reads EXABEAM_MCP_URL, EXABEAM_API_KEY and EXABEAM_API_SECRET from the environment first, and falls back to the file for whatever the environment did not supply. So if you already run Vault, AWS Secrets Manager, SOPS or a keychain helper, export them at process start and keep no file at all:

bash export EXABEAM_API_KEY="$(vault kv get -field=key secret/exabeam)" export EXABEAM_API_SECRET="$(vault kv get -field=secret secret/exabeam)"

The environment wins, so a stale file left from an earlier install cannot silently override a live broker. An empty variable counts as unset, so EXABEAM_API_KEY= in a shell profile does not blank out a working file. Set none of them and nothing changes.

preflight.sh and the connector's startup line both name which source supplied each setting (names only, never values), so you can confirm the broker is actually being used.

What this does and does not buy. It does not make the environment safer than the file in general — both are readable by anything running as you. What it removes is the file-at-rest exposure: backup and sync agents that sweep your home directory, crash dumps, an accidental cat or screen share, and home-directory archives taken for support or migration.

3. Check the setup. The plugin ships a read-only diagnostic that tells you what, if anything, is missing. It lives in the installed plugin. Run it with the exact version step 1 showed (not a wildcard: the cache keeps earlier versions, and a wildcard would run the oldest one):

bash ~/.claude/plugins/cache/open-agent-ai-security/raffkin/<version>/preflight.sh

Expect ✓ on every line, including Exabeam MCP reachable and Human-in-the-loop gate ON. A ! or ✗ line names what to fix; a ↷ line was skipped because an earlier line failed, so fix that one first. If you see No credentials yet, go back to step 2.

4. Run your first investigation. Start Claude Code and hand it an alert:

investigate alert <alert id>

You can find an alert ID in the New-Scale console under Threat Center → Alerts; or ask Raffkin "triage the queue" first and pick one from the list it returns. Raffkin loads the soc-investigate skill, queries Exabeam for the evidence (you will see the tool calls go by), and ends with a written report: the timeline, the evidence with its source, a MITRE mapping, a verdict, and a last line of Taxonomy outcome: raised, auto_closed or fp_closed. If it concludes the alert is a false positive, it asks you — "Dismiss alert X as a false positive? (yes / no)" — and waits. Nothing is dismissed or closed until you say yes.

That is the whole setup. Using the skills covers what else you can ask.

Quick start — Codex

1. Install the plugin.

codex plugin marketplace add open-agent-ai-security/plugins
codex plugin add raffkin@open-agent-ai-security
codex plugin list      # expect: raffkin@open-agent-ai-security  installed, enabled  <version>

2. Add your credentials — the same file as for Claude Code, above (~/.exabeam-mcp.env, https://, chmod 600). Then start a new Codex session.

3. Check the setup. codex plugin list prints the plugin's path in its last column. Run the diagnostic from there:

bash <that path>/preflight.sh --platform codex

Expect ✓ on every line, including Exabeam MCP reachable and Human-in-the-loop gate ON. A ! or ✗ line names what to fix; a ↷ line was skipped because an earlier line failed, so fix that one first. If you see No credentials yet, go back to step 2.

4. Run your first investigation. In a Codex session:

investigate alert <alert id>

Same report, same last line, same question before any dismissal. One difference on Codex: it also asks you before Raffkin opens a case or writes a note, because Exabeam marks those tools as writes and Codex asks before every write. Noisier, not less safe. And if you script Raffkin with codex exec, where nobody is at the keyboard, Codex cancels any write that needs an approval rather than letting it through — the gate does not evaporate when the human does.

Quick start — Google Antigravity

1. Install the plugin. Antigravity installs from a GitHub subpath into ~/.gemini/config/plugins/:

agy plugin install https://github.com/open-agent-ai-security/raffkin/tree/main/plugin

Read what it prints, because this is the earliest point at which a missing piece is visible:

  [ok]    raffkin
          ✔ skills      : 3 processed
          - agents      : skipped (not found)
          - commands    : skipped (not found)
          ✔ mcpServers  : 1 processed
          ✔ hooks       : 1 processed

mcpServers : 1 is the Exabeam connection and hooks : 1 is the safety gate. If either says skipped, stop: the skills will load and have nothing to call, or they will load with no gate in front of them. agy plugin list --json shows the same thing afterwards, and names the gate ("hooks": ["<this plugin's name>-gate"]).

2. Add your credentials — the same file as the other hosts (~/.exabeam-mcp.env, https://, chmod 600).

3. Check the setup.

bash ~/.gemini/config/plugins/raffkin/preflight.sh

Expect ✓ on every line, the gate included. The script detects Antigravity from its own install path, so --platform antigravity is only needed if you run a copy from somewhere else. If the gate line reports a !, read it: the likeliest cause is that neither python3 nor uv is on the PATH the host launches hooks with, and the gate cannot run without one of them.

4. Run your first investigation. In an Antigravity session:

investigate alert <alert id>

Where this install comes from

Antigravity has a Marketplace, but no catalog you add yourself: there is no agy plugin marketplace add, so agy installs the directory the URL points at, and the plugin lands in ~/.gemini/config/plugins/ under its manifest name.

This is the community build, from the plugin's own source repository. The Exabeam-supported build is a vendored copy of the same tree, served from the Exabeam Plug-in Catalog under its own terms and support, and it has its own install command.

What is different on this host

Raffkin's three skills, the Exabeam connection and the human-in-the-loop gate all work here. The gate is the same file as on Claude Code, it reads the same tier file, and every decision lands on the same audit trail. Antigravity loads it from hooks.json at the plugin root; a fresh install reports it (hooks : 1), preflight.sh makes it refuse a containment call, and it has now been observed being called in a live session.

One difference is not a gap in testing but a difference in what is enforced, and you need it before you choose how to run this host. On Antigravity the gate's ask does not survive --dangerously-skip-permissions. We measured it: a session started with that flag completed an ask-tier case closure one second after the gate asked, with nobody prompted. The host's own documentation describes deny as a hard block and ask as "prompt the user", and the flag auto-answers the prompt. So on this host:

  • the deny tier holds. Probed directly — a stub hook returning deny under that flag blocked the call — so the one guarantee this plugin rests on, that containment is never executed, survives an operator turning permissions off;
  • the ask tier is enforced in a normal session and is not enforced under that flag. Neither is force_ask, the decision the host documents as "always prompt the user, ignoring cached permissions". Both were probed and both were overridden, so there is no hook-level way to force a prompt on this host once that flag is set. One limit of that measurement: a tool that ran under the flag cannot tell us whether the host recognised the decision and auto-approved it, or did not recognise it and treated it as no objection. Either way the call was not stopped;
  • a completed ask-tier call is therefore recorded as ran_consent_unconfirmed rather than approved, because the gate cannot see whether a human answered. An approved line is evidence of consent; that line is not.

If you run this host unattended, do not rely on the ask tier to hold. Use a key whose entitlements cannot perform what you are unwilling to have happen without a human — that control does not depend on any host. See Key entitlements.

Two further differences are worth knowing before you run an investigation on this host.

No release has been red-teamed on a Gemini model. Every Raffkin release is adversarially tested on the weakest supported model of each host before it ships, and that work has been done on Claude and GPT models only. The gate is a control on the tool call, so it does not depend on the model's good behaviour — but prompt-injection resistance, refusal discipline and how the skills hold up under pressure are all model properties, and on this host they are untested. That is a gap in our evidence, not a known weakness.

The gate needs an interpreter, and this host bundles neither. The hook runs under python3, falling back to uv, which the Exabeam connector already requires. If both are missing the hook refuses the call outright — the refusal is written by the shell, not by the gate, and says which interpreters it looked for. That is deliberate and it is host-specific: on Claude Code a hook whose command fails blocks the call by exiting 2, but Antigravity reads a decision on standard output and nothing else, so a gate that cannot start would otherwise be a gate that is never heard. preflight.sh checks for an interpreter and says so, and it is worth running once after you install.

The one case the refusal does not cover is the host killing the hook at its 20-second timeout, which takes the shell with it. Nothing has been observed to take that long: the gate reads one JSON object, compares a tool name against a static tier file and writes a line.

One smaller difference shows up in the log rather than in what is enforced: Antigravity does not tell a hook which permission mode the session is running in. On Claude Code that lets the audit trail distinguish an ask a human answered from one that completed in an unattended mode; here the gate cannot make that distinction, so it does not claim it — see ran_consent_unconfirmed above. Records written on this host carry "host": "antigravity" so the log never has to be guessed at.

What runs identically on every host, because it lives in the connector rather than the host: what the model reads is screened for injected instructions, what it writes back is neutralized and masked, a create_case carrying a closing disposition is refused, and every call is on the audit trail.

Your key is still the limit worth setting. Entitlements are enforced by Exabeam, not by the host, so they hold even if a host control is misconfigured — the gate denies a rule write, and an unentitled key means there is no rule-write tool to deny in the first place. rule-tuning only ever needs reads, so there is no reason to entitle the key for detection-content writes. See Key entitlements.

The gate has now been driven in a live agy session (1.4.5, 2026-10-22), which is what settled the question that mattered most: the host does call the hook, and the gate reads the step it is handed. The payload was captured and is now a test fixture, because it did not match the host's documented contract — the tool call's keys are PascalCase (ServerName, ToolName, Arguments) where the hook documentation says camelCase, the tool name sits beside the server rather than nested, and arguments arrive positionally wrapped. Read the documented way, the server went unseen: allow-tier reads got no decision and a containment tool named in its bare form (isolate_host) got none either. That is fixed and pinned by tests against the captured payload.

One behaviour to know, because it is not a defect and will look like one: on this host the gate's allow is not a permission grant. It restricts; it does not entitle. Antigravity's own permission system still applies on top, and a headless agy -p session cannot prompt for the mcp permission, so it auto-denies the call even when the gate has allowed it. Interactively you are asked. On Claude Code the plugin ships a permission snippet that grants the allow tier; there is no equivalent to ship here yet.

One thing remains unexercised: what the host's own prompt looks like on an ask in an attended session. Whether a deny holds under --dangerously-skip-permissions is no longer open — it was probed directly and it holds, which is the measurement the section above rests on. The open item is tracked in raffkin#305. Moving the deny tier into the connector as well, so it holds without depending on any host, is raffkin#308.

Updating

# Claude Code
claude plugin marketplace update open-agent-ai-security
claude plugin update raffkin@open-agent-ai-security

# Codex
codex plugin marketplace upgrade open-agent-ai-security
codex plugin add raffkin@open-agent-ai-security

On Antigravity there is no catalog to refresh — re-run the install command, which re-reads the source:

agy plugin install https://github.com/open-agent-ai-security/raffkin/tree/main/plugin

Both commands matter on Claude Code: the first refreshes the catalog, the second installs from it. Restart or /reload-plugins to apply. Auto-update on Claude Code is per marketplace and off by default for marketplaces you add yourself; turn it on under /plugin → Marketplaces → open-agent-ai-security, or fleet-wide in a managed settings.json:

{
  "extraKnownMarketplaces": {
    "open-agent-ai-security": {
      "source": { "source": "github", "repo": "open-agent-ai-security/plugins" },
      "autoUpdate": true
    }
  }
}

Troubleshooting

Run preflight.sh first (step 3 above); it checks the CLI, uv, the credentials file, the connection to your tenant, and the safety gate, and names the failing step.

  • Exabeam MCP reachable fails. The region in EXABEAM_MCP_URL is the first thing to check: it must be the region from your console address, not the country shown in License View. Then check that the URL starts with https:// and that the key and secret are the ones your console shows. The connector refuses to start over http://, on purpose.
  • Investigations work but rule-tuning returns nothing. The key is entitled for alerts and cases but not for detection content. An under-entitled key installs and connects cleanly, and the reads it lacks may come back empty rather than failing. See Key entitlements.
  • The skill says the Exabeam MCP is not connected. The credentials file is missing or was added after the host started; add it and restart the host.
  • claude plugin list shows an error beside Raffkin. The plugin installed but did not load; run claude plugin update raffkin@open-agent-ai-security to get the current release, then restart.
  • On Codex, no exabeam server appears. Codex drops a bundled server silently if any part of its configuration is invalid; run codex plugin add raffkin@open-agent-ai-security again and re-check.

Advanced: wiring the Exabeam MCP by hand (not recommended)

You can register the remote Exabeam MCP in your host directly (claude mcp add … exabeam …) with a bearer token you mint yourself. Two things to know: the token expires in about four hours, and, more importantly, Raffkin's guardrails — the screening of what it reads, the neutralizing and masking of what it writes, and the audit trail — live in the bundled connector, so none of them run when Claude Code talks to the remote MCP directly. Only the dismiss/close gate survives, and only if the server is named exabeam. Use this for a connectivity check, not for investigations you rely on.

Key entitlements

Whoever grants the key's access entitlements can check against this list rather than guessing. These are the Exabeam MCP tools Raffkin calls, shown without their exabeam_ prefix. Any tool not on this list asks you first, and on every host each containment or rule-writing tool is refused by the gate before it reaches your tenant. Entitling the key to nothing beyond this list is the control that holds even if a host control is misconfigured, so do it whichever host you use.

Needed for Tools
Investigating alerts and cases search_alerts, get_alert_details, get_alert_threat_timeline, search_cases, get_case_details, get_case_notes, get_case_threat_timeline, search_events, threat_summary, get_mitre_coverage, get_correlation_rule_details
Rule tuning analytics_rule_list, analytics_rule_details, correlation_rule_list, parser_list, get_parser_details, context_table_list, get_context_table_records, get_use_case_score
Recording an outcome create_case, create_case_notes (allowed as escalation); update_alert, update_case (always ask you first)
Optional send_email (always asks you first; everything else works without it)

Uninstalling

# Claude Code
claude plugin uninstall raffkin@open-agent-ai-security
claude plugin marketplace remove open-agent-ai-security   # optional; also removes other plugins from this catalog

# Codex
codex plugin remove raffkin@open-agent-ai-security
codex plugin marketplace remove open-agent-ai-security   # optional; same caveat

On Antigravity the plugin is named, not keyed to a marketplace:

agy plugin uninstall raffkin

Removing the plugin removes the gate it shipped, on every host. None of the three commands touches ~/.exabeam-mcp.env; delete that yourself when you are done with the credentials.
